# Матриця рольового доступу

Актуально станом на 19 червня 2026 року. Матриця є нормативною для backend guards, frontend routes і UI actions.

Ролі не успадковують дозволи одна від одної. Кожен endpoint повинен явно перелічувати дозволені ролі, а доступ до конкретного об'єкта додатково обмежується академічним scope.

Позначення: `R` — перегляд, `W` — створення або зміна, `O` — лише власні чи призначені об'єкти, `S` — організаційний scope, `—` — доступу немає.

## Критичні правила

1. Ректор не має доступу до створення, редагування, зміни ролей або блокування користувачів.
2. Президент має лише read-only пошук студентів; інші облікові записи не повертаються його user endpoints.
3. Розклад змінює лише адміністратор. Інші ролі можуть тільки читати дозволений їм scope.
4. Ректор і президент переглядають агреговані звіти та результати опитувань, але не виконують операційні мутації.
5. `department_head` і `dean` не отримують автоматично права викладача: потрібна явна роль у decorator і перевірка scope сервісом.
6. Frontend visibility не є захистом. Кожне правило дублюється backend guard та, де потрібно, object-level перевіркою.

## Регресійні перевірки

- `roles.guard.spec.ts` перевіряє відсутність неявного успадкування для кожної ролі.
- `identity.e2e-spec.ts` перевіряє, що ректор не може редагувати або блокувати користувача.
- `schedule.e2e-spec.ts` перевіряє administrator-only мутації розкладу.
- `academic-access.e2e-spec.ts` перевіряє object-level scope студентів, викладачів, кафедр і факультетів.
